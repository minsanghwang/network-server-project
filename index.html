더 큰 기업을 모델로 잡았다가, 본사 1곳과 지사 3곳으로 규모를 줄였습니다.

처음에는 훨씬 큰 규모의 기업을 모티브로 하려 했습니다. 그렇게 하면 각 거점이 독립된 본사 규모가 되어, 지사를 두는 구조가 아니라 본사 여러 곳을 서로 잇는 구조가 됩니다. 그래서 본사 아래에 지사를 두는 구조가 되도록 규모를 축소했습니다.

네트워크 설계

Core, Distribution, Access 3계층과 이중화

2계층에서 3계층으로 재설계

처음에는 Core가 Distribution 역할을 겸하는 Collapsed Core로 구축했습니다. 부서별 PC가 늘면 모든 Access를 Core에 직결해야 해서 포트와 이중화에 한계가 있었고, Distribution 4대를 추가해 3계층으로 바꿨습니다.

구분변경 전변경 후
게이트웨이 (SVI + HSRP)Core-SW1, 2Dist-SW1~4
Core 역할라우팅과 VLAN 게이트웨이백본 라우팅만 담당

설계 결정

  • Core 양쪽 연결. 각 Dist를 Core-SW1과 Core-SW2에 모두 연결했습니다. Core 한 대가 내려가도 OSPF가 우회 경로를 고르고, 주요 경로는 ECMP로 양쪽에 등록됩니다.
  • 라우팅 전용 VLAN. c3745의 NM-16ESW 포트는 L2 전용이라 no switchport로 라우팅 포트를 만들 수 없고 내장 L3 포트는 2개뿐이었습니다. VLAN 400~403을 L3 링크용으로 두고 SVI로 연결해 포트 제약을 피했습니다.
  • 게이트웨이 이중화. Dist 쌍마다 HSRP를 적용했습니다. Active는 priority 110, Standby는 90이고 preempt로 장애 복구 후 원래 Active가 역할을 되찾습니다.
  • OSPF Area 0. WAN-IT, Core, Dist 전체가 한 영역에 있고, 사용자 VLAN은 passive-interface로 인접 형성을 막았습니다.

DHCP

  • VLAN 410~450에 각각 .11~.200 범위를 할당했고, 서버존은 고정 IP로 운영합니다.
  • 게이트웨이로 HSRP VIP를 내려주기 때문에 Dist 장애 때도 클라이언트 설정을 바꿀 필요가 없습니다.
  • 클라이언트와 서버가 다른 서브넷이라 Dist-SW SVI에 ip helper-address로 Relay를 구성했습니다.

웹 서비스 두 개

Cooping 쇼핑몰 (shop.it.cooping.com). 상품, 장바구니, 주문과 결제, 환불까지 직접 구현했고 DB 테이블은 8개입니다. 주문 처리는 SELECT ... FOR UPDATE로 재고를 잠근 뒤 차감하는 트랜잭션입니다. 물류센터와 형식을 맞춰, 물류 시스템과 키 값으로 바로 매칭할 수 있습니다.

QA 시스템 (qa.it.cooping.com). 물류센터의 파손과 분실 건을 조회하고 미확인, 처리중, 보류, 완료, 반려 5단계로 처리 상태를 관리합니다. 물류센터 실 DB가 준비되기 전이라 같은 구조의 mock DB로 개발했고, 연동 지점을 DB 접속 정보 한 곳에 모아 실 DB로 바꿀 때 화면 코드를 고치지 않아도 됩니다.

두 사이트 모두 Apache 가상호스트에서 Require ip로 접근 대역을 제한합니다.

  • 제외한 게이트웨이 3개는 HSRP VIP .1과 Dist 두 대의 SVI .2, .3입니다.
  • VLAN을 추가하면 VLAN당 251대씩 늘어납니다. 10.14.0.0/16에는 사용 중인 7개 블록(링크용 10.14.0.x, 410~450, 490)을 빼고도 /24가 249개 남아 있고, /16 전체의 이론 상한은 65,534개 주소입니다.
  • 실제 상한은 스위치 포트입니다. Access 스위치가 NM-16ESW 1개에 업링크 2개를 쓴다고 가정하면 스위치당 14대, 5대 합쳐 70대입니다. 이 값은 가정이라 장비 구성을 확인해야 합니다.

개발 구간에 인프라 PC를 꽂으면 인프라 대역에 접속할 수 있나

접속할 수 있습니다. 포트의 VLAN만 바꾸면 인프라 네트워크를 그대로 쓸 수도 있습니다.

VLAN 간 통신은 Dist-SW1의 SVI에서 라우팅되고 VLAN 간 ACL은 없습니다. Access와 Dist 사이 트렁크는 인프라 VLAN(420)을 포함해 사용자 VLAN을 모두 통과시킵니다.

개발 포트(VLAN 410)에 연결포트를 VLAN 420으로 변경
필요한 설정없음포트에 switchport access vlan 420 한 줄
받는 IP10.14.10.11~20010.14.20.11~200

  • 접근 권한이 사람이 아니라 IP 대역을 기준으로 정해집니다. 인프라팀 사용자가 개발 포트에 연결하면 개발 대역 IP를 받아 쇼핑몰 접근 제어를 통과합니다.
  • 인프라팀이 개발 구간에서 일해야 하면 그 포트를 VLAN 420으로 바꾸면 됩니다. 트렁크가 VLAN 420을 이미 통과시키므로 배선이나 트렁크는 건드리지 않고, Access-SW1에 VLAN 420이 등록되어 있기만 하면 됩니다.
  • 호스트 방화벽(firewalld)이나 이후에 추가하는 ACL이 있으면 결과가 달라집니다.

트러블슈팅

설계 단계의 규모 문제를 먼저, 이어서 실무에서도 일어나는 장애를 정리했습니다.

Collapsed Core 구조의 규모 한계

상황
처음에는 Core가 Distribution 역할을 겸하는 2계층(Collapsed Core)으로 설계해 구축했고, 모든 Access를 Core에 직결했음
문제
부서별 PC가 늘어나는 규모를 설계 때 산정하지 않아, Access를 늘릴수록 Core의 포트가 모자라고 게이트웨이와 이중화가 Core 두 대에 몰리는 구조였음
해결
Dist 4대를 추가해 Core 양쪽에 연결하고 게이트웨이(SVI + HSRP)를 Dist로 옮김. NM-16ESW 포트가 L2 전용이라 라우팅 전용 VLAN(402, 403)과 SVI로 L3 링크를 구성. 운영 중인 DHCP, DNS, 웹 서비스를 중단하지 않고 전환
결과
Core 단일 장애 시 OSPF가 우회하는 것을 검증했고, Access 스위치를 늘려도 기존 서비스에 영향이 없는 구조가 됨. 사용자 수, 포트 수, 이중화 수준을 먼저 정하고 계층을 정해야 한다는 점을 배움

WAN 구간 편도 통신

증상
다른 지사로 ping을 보내면 나가기만 하고 응답이 돌아오지 않음
원인
static default route는 나가는 경로만 정의해서 상대 라우터가 10.14.0.0/16으로 돌아오는 경로를 몰랐음
해결
WAN 구간을 OSPF Area 0에 넣어 양쪽이 서로의 대역을 자동으로 학습하게 변경

DHCP 서비스가 재부팅 후 꺼져 있음

증상
클라이언트가 169.254.x.x(APIPA) 주소를 받음
원인
서버 로그에 DHCPDISCOVER가 도달하지 않아 Relay 경로를 먼저 의심했으나, 재부팅 후 dhcpd가 자동 시작되지 않는 상태(disabled)였음
해결
systemctl enable dhcpd로 자동 시작을 등록하고, named, httpd, mariadb도 함께 점검해 enable

가상 환경에서만 생긴 문제

  • GNS3 노드의 디스크 용량이 부족해 vlan.dat 저장이 실패하고, 재부팅마다 VLAN이 사라져 HSRP가 Init이 됨. 디스크를 32MiB로 늘리고 VLAN 작업 뒤 dir flash:를 확인
  • GNS3가 비정상 종료된 뒤 VirtualBox 서버와의 링크가 단방향으로만 동작. GNS3를 재시작하고, 케이블은 VM을 멈춘 상태에서 연결
  • 가상 경로의 MTU 문제로 패키지 설치가 중간에 멈춤. MTU를 1400으로 낮춰 해결

보안 영역을 제외하고 만든 프로젝트입니다.

Firewall, DMZ, VLAN 간 ACL, 웹 서버 IP 직접 접속 차단(firewalld)은 이번 범위에 넣지 않았습니다. 그래서 VLAN 간 통신은 제한하지 않았습니다.

GNS3 가상 환경에서 구축한 팀 프로젝트이며, 도메인과 IP는 실습용입니다.
